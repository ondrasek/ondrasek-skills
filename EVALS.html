Evals of agent skills: a map

What the six eval harnesses of this repository measure, how far each number can be trusted, and what you can learn from the way they were built. Structured as a map: the anatomy of a score, how to earn trust in a grader, the parts of the harness, a filterable set of topic cards, a dated timeline, and what to carry away.

Compiled 23 November 2026 from the repository as of 22 November 2026 · real runs 4 to 22 November 2026 · Claude Code 2.1.330 unless a line says otherwise. The structure follows the public page "Evaluations State of the Art Map" (author unknown); none of its figures or claims are reused here.

The formula and the legend

score = f( skill + plugin, model, harness, task set, grader, sampling noise ) In this project the thing under test is the skill or plugin (its text, scripts and hooks). The model family and Claude Code 2.1.330 are held fixed. Every number below is conditional on that.
Trust labels
  • established measured here in real runs, or documented by Claude Code's own documentation
  • contested measured once, or reasonable people could disagree
  • my inference reasoned, not measured
  • not yet checked a known gap
Tracks
  • MODEL depends on what the model does: wording, flakiness, sample noise
  • HARNESS depends on Claude Code or on our runner: permissions, hooks, graders, snapshots
  • BOTH cannot be separated
Verdicts of a trial
  • PASS every deciding check holds
  • FAIL a deciding check fails and nothing explains it away
  • INCONCLUSIVE the behaviour under test never happened (a hook errored, a call was denied, the run crashed)

What is evaluated

Six plugins have a harness each under evals/<plugin>/, sharing one module, evals/_common/ (the stream-json reader and the command runner). Each harness builds a throwaway workspace, runs the real agent headless on a fixed prompt, and grades the state the agent left behind.

1. Anatomy of a score

A score is the end of a chain of six decisions. Select a stage to see what it is here, how it fails, and where our evals stand.

Construct

What are we trying to measure?

What it is here
The promise of each plugin, stated in its SKILL.md or hook: "one item, one question per message", "propose first, change nothing before approval", "the hook report makes the agent save the work", "a blocked rewrite stays blocked". The construct is the promise, not a sentence the model happens to write.
How it fails
A check measures a proxy of the promise. "Exactly one question mark" is a proxy for "one question": a correct reply that quotes a URL with ? fails it, a sneaky second question without a mark passes it.
Where we stand
Each harness README states the promise and lists every check against it. Checks decided by state (files, git history, the remote, the tracker) match the promise closely; checks on the model's wording are proxies, so they are demoted to advisory (see stage 4). No user study has asked whether the promises are the right ones.
BOTHcontested evidence: the "Checks" tables in oaat and auto-commit

Task set

Which items stand in for it?

What it is here
46 cases in six CSV files: explicit, implicit and contextual prompts, follow-ups (skip, stop, tangent, approval), and negative controls where the skill must stay silent or change nothing. Workspaces are invented and generated by code in a temporary directory; nothing is a copy of a real project.
How it fails
Cases were chosen by hand (convenience sampling). Once every case passes, the set cannot separate a good version from a slightly worse one (saturation). The repository is public, so a future model could see the cases.
Where we stand
All 46 cases passed in the last real runs, so the set works as a regression guard, not as a ranking instrument. Two cases earned their place by exposing real problems: with-milestones (the agent skipped a file that held open questions) and create-tracker (the model chained calls through a shell variable). Whether 46 hand-picked cases represent real use is not checked.
BOTHestablished (counts) not yet checked (representativeness)

System under test

Skill inside which harness?

What it is here
The plugin loaded with --plugin-dir, the model, Claude Code 2.1.330, and the permission mode with its allow-list. The user's own settings are left out (--setting-sources project,local).
How it fails
A score is credited to the skill when the permission mode produced it. Inside the Claude Code sandbox, hooks could not run at all (they could not create their data directory) and a session could not be resumed. Under dontAsk, three shapes were denied that no allow-list pattern could permit: output redirects, shell-variable calls, and reads outside the working directory.
Where we stand
Measured with small probes of the real CLI. Real runs must be started outside the sandbox. The git harnesses run under acceptEdits; sitrep also adds its plugin directory with --add-dir. Every README records the exact command and version.
HARNESSestablished evidence: Lessons in the auto-commit and milestones READMEs

Grader

Who decides pass or fail?

What it is here
Small pure functions over the recorded trace and the before/after snapshots. Checks sit in groups: precondition, process, gate, outcome, apply, and an advisory soft group (WARN, never decides). The verdict is PASS, FAIL or INCONCLUSIVE.
How it fails
False positives and false negatives. Real examples: a tangent reply that correctly names the current item as "Item 1 of 5" was failed by a header regex; a denied-then-retried command made a fully valid sitrep trial INCONCLUSIVE; early drafts of prose checks passed a lying reply.
Where we stand
Every check has an invented failing run enforced by a test. Independent model reviewers read the code on disk over several rounds and found real bugs each time; the fixes are in. Prose checks cannot be made both strict and fair, so they only warn. The recorded real trials are re-gradable offline, which is how the two false verdicts above were confirmed and fixed.
HARNESSestablished (tested) contested (reviewers were models, no human audit)

Statistics

How sure is the number?

What it is here
Pass counts per case and trial, 1 to 5 trials per case. No standard errors or intervals are reported in the READMEs. Cases are run again after a change to see a before/after difference.
How it fails
A clean run is read as proof. If a case truly fails 40% of the time, three trials still all pass with probability 0.63 = 21.6%. With zero failures in n trials, the one-sided 95% upper bound on the failure rate is 1 − 0.051/n: about 63% for n = 3 and about 9.5% for n = 30 (and the 30 are not independent draws from one population: they are 10 cases times 3).
Where we stand
Three clean trials per case rule out frequent failure, not rare failure. Before/after comparisons were large (0 of 3 to 3 of 3, 1 of 5 to 5 of 5) but were not tested for significance. Sample size was a budget choice (about $0.04 to $0.25 per trial).
MODELestablished (the arithmetic) not yet checked (intervals are not reported)

Claim

What may we conclude?

What it is here
The sentence in a README status line, for example "milestones: 30 of 30 trials pass on Claude Code 2.1.330".
How it fails
The claim is wider than the evidence: "the skill works" from invented traces; "the tool path works" for oaat, when headless runs cannot call that tool at all (measured: it is absent in claude -p).
Where we stand
Every README separates what real runs confirmed from what is still unconfirmed. The oaat tool path is graded only on invented traces plus one observed answer format, and the README says so in capitals.
BOTHmy inference evidence: the "Unconfirmed" lists in every README

2. Graders: how to earn trust in a judge

A grader is a classifier: it labels a run pass or fail, and it can be wrong. Our graders are mostly deterministic code, plus one optional model judge and a set of prose checks that behave like cheap judges. The loop below is the way to earn trust in any of them; each step says what we did and what we did not.

Criterion

One narrow pass or fail question

What we did
Every check has an id and answers one question, for example remote-unchanged (is the remote ref the same as before?), skip-last (is the last option exactly "Skip for now"?). Each returns a pass flag and a note that says what it saw.
How it breaks
A criterion that bundles two questions fails for either and hides which.
Status
Done for the code graders. The optional oaat rubric judge restates the skill's rules in its own criteria list.
HARNESSestablished

Gold labels

Experts label a random sample

What we did
We did not have experts label a random sample. Our gold labels are (a) invented good runs and invented bad runs built by editing a good one, one per check, and (b) real recorded traces that were regraded offline after each grader fix.
How it breaks
Labels written by the same author as the grader share its blind spots, and invented bad runs are the bad runs the author imagined.
Status
The independent reviewers wrote their own bad runs, which is the nearest thing to outside labels: they found false negatives the author had not imagined. No human-labelled random sample exists.
HARNESScontested

Grader design

Rubric, examples, which model

What we did
Code graders as pure functions with regexes that are tested on both a passing and a failing text. The oaat harness also has an optional second model call that fills a JSON schema (overall_pass, a score, one entry per criterion); its prompt can be printed offline.
How it breaks
A model judge is a second noisy measurement and can disagree with the code checks.
Status
The judge is exercised in the tests with a stub judge only. None of the live runs reported here used it.
MODELnot yet checked (live judge)

Measure the grader

Treat it as a classifier

What we did
Reviewer probes: independent reviewers built traces that a check should pass or fail and ran them. The reviews found concrete errors in each round (a correct reply failed, a lying reply passed, a verdict that masked a real failure, a call after a template item that went unflagged).
How it breaks
Probes show that errors exist, not how often they occur.
Status
No precision or recall was measured on a labelled sample.
HARNESSnot yet checked (as rates)

Correct the estimate

Report a bias-corrected score

What we did
Nothing statistical. Pass rates are raw. What we did do is fix a grader and regrade the recorded runs: for example discover-open-items read 4 of 5 with one trial graded INCONCLUSIVE, and 5 of 5 after the retry rule was fixed.
How it breaks
Regrading after seeing the result invites fitting the grader to the answer. We limited it to cases where the reply was demonstrably valid and recorded the change.
Status
No bias-corrected estimate with an interval.
BOTHnot yet checked

Know its limit

Where the grader cannot decide

What we did
Three explicit places for "cannot decide": the INCONCLUSIVE verdict for environment failures; the advisory (WARN) group for wording; and a list of known residual gaps per README, for example a push hidden inside a heredoc, or a tangent flag whose item name contains a full stop.
How it breaks
A limit that is written down but never read.
Status
Every README lists its unconfirmed facts and known limits.
HARNESSestablished

3. Inside the harness

"The harness" has two meanings here: Claude Code around the model, and our runner around Claude Code. Each part can be evaluated alone by holding the model and the tasks fixed and changing only that part. Select a part.

Instructions

System prompt and examples

What it is here
The text of SKILL.md and the prompt of each case.
How it breaks
One sentence changes behaviour in a way a diff does not show.
Isolated evaluation
Change one instruction, hold model and cases fixed, repeat. milestones: asking the model to write the script path out in every call took update-finish-and-start from 0 of 3 to 3 of 3; a worked example of a chained create took create-tracker from 1 of 3 to 3 of 3 (and 3 of 3 again in the repeat pass). sitrep: a sentence telling the agent to look in the working tree took the vague-prompt case from 1 of 5 to 5 of 5.
MODELestablished (large effects, small samples)

Tools

What the agent can call

What it is here
The allow-list, the permission mode and which tools exist at all. --allowedTools, --permission-mode (dontAsk or acceptEdits), --add-dir.
How it breaks
A denied call makes the agent give up on a whole tool, and the trial then measures the allow-list. The question tool does not exist in headless runs.
Isolated evaluation
A handful of one-command probes against the real CLI settled which command shapes each mode permits. oaat's AskUserQuestion is not in claude -p (one probe: the model's search for it found nothing), which is why its tool path can only be graded on invented traces.
HARNESSestablished

Context window

What stays in view, compaction

What it is here
What the agent sees at the start of a trial: the plugin, the fixture, the prompt. Isolation keeps the user's settings, hooks and plugins out, and unsets CLAUDE_PROJECT_DIR so a hook cannot look at the repository the harness was started from.
How it breaks
The user's own ~/.claude/CLAUDE.md leaks into recorded traces; an inherited environment variable redirects a hook.
Isolated evaluation
Compaction is not evaluated: trials are short. Two-turn cases use a resumed session, where the second turn's result event already reports the whole session's cost (a real trace: $0.0906, then $0.1201 for the same session).
HARNESSestablished (isolation) not yet checked (compaction)

Memory

What persists across sessions

What it is here
Nothing carries over between trials by design: each trial gets a fresh workspace. What does persist is the plugin's own state, for example .cache/milestones.json, which the harness builds in code for each case, and the saved session that a second turn resumes.
How it breaks
Inside the sandbox the session store cannot be written, so the second turn fails with "No conversation found".
Isolated evaluation
The milestones cases vary the tracker (fresh, stale, blocked) and grade the file afterwards, with other items required to be untouched.
BOTHestablished

Handover

Passing work on

What it is here
Four handovers: a hook's report back to the agent (a Stop hook that exits with code 2 continues the run, documented and observed), the approval message of turn 2 (stated by content, because the model numbers its proposals differently every run), the answer of the question tool (returned inside the same turn), and sub-agents.
How it breaks
Work done in a sub-agent is invisible in the main trace, so a trace-only grader would miss it.
Isolated evaluation
This is the reason the ground truth is the file and git snapshot, not the transcript. The observed answer format of the question tool is a wrapper sentence, not a bare label; the harness parses it and labels it unconfirmed across versions.
HARNESSestablished (hooks) contested (question-tool envelope: one sample)

Orchestration

Loop, sub-agents, topology

What it is here
The loop that hooks create (a Stop hook can make the agent continue, up to a documented cap of consecutive continuations), and the runner's own loop: trials, a per-call budget cap of $2 and a timeout.
How it breaks
A hook that errors before it runs looks like a plugin that failed to block anything.
Isolated evaluation
The hook events appear in the trace (hook_started, hook_response with exit code and outcome), so a hook error (an exit code other than 0 or 2) becomes a precondition: the trial is INCONCLUSIVE, not a plugin failure. The harnesses themselves were built by a pipeline of models in assigned roles (research, plan, build, review, fix) with human-approved decisions.
HARNESSestablished

6. What to carry away

6.1 Seven working rules

  1. Ask what was held fixed. A score with no named version, permission mode and plugin version is a claim about an unknown system. Every README here names them.
  2. Ask for the interval. Three clean trials do not exclude a failure rate of about 63%; thirty pooled trials, about 9.5%. A pass count is not a rate.
  3. Ask how old and how public the tasks are. These cases are invented and built in code, but the repository is public, and a case that always passes cannot show a small regression.
  4. Ask who checked the grader. A grader is software and has bugs. Ours were tested with a failing run per check and probed by independent model reviewers; nobody labelled a random sample by hand.
  5. Ask who ran it. The author directed the work and models built, ran and reviewed it. There is no independent replication.
  6. Ask how the judge was validated. The code graders were; the optional model judge of oaat was not (only a stub in tests), and the prose checks are advisory for that reason.
  7. Ask what survives a context reset. Constraints that live only in a conversation are lost first. Here the record lives in the READMEs, the tests and the git history; recorded traces live in git-ignored artifacts/ and are gone after a fresh clone.

6.2 What is still unchecked

  • The real stream of the question tool in an interactive session: only its input shape (documented) and one answer format (observed once) are known.
  • The optional model judge of oaat against human labels.
  • Precision and recall of any grader on a labelled random sample.
  • Representativeness of the 46 hand-picked cases for real use.
  • Any Claude Code version other than 2.1.330, and any model other than the one used. Hook and permission behaviour is "confirmed" only for that version.
  • Whether --setting-sources project,local keeps user-level hooks out on every machine: confirmed by counting hook events in the recorded traces here only.
  • The link of the Google post cited below was not re-verified for this document.
  • Independent replication: none.

6.3 Check question, answered

Question. A teammate says: "milestones passes 30 of 30 trials, so the skill is fixed." Name two things you need to know before accepting that, and the track each belongs to.

Answer. The claim does not follow as stated. Any two of these four are a correct answer, and the first two matter most.

  1. Which system ran, in which harness. HARNESS The 30 trials ran on Claude Code 2.1.330 under dontAsk with a specific allow-list, outside the sandbox. In the sandbox the same cases could not run at all, and before the skill edit the same cases and harness gave 0 of 3 on two of them. The result holds for that setup only.
  2. How uncertain the number is. MODEL That is 10 cases, 3 trials each. For one case, 3 of 3 clean trials still allow a true failure rate of about 63% (one-sided 95%). Even pooling all 30 as if independent, the bound is about 9.5%, and they are not independent draws. "No failure seen" is not "no failures".
  3. Whether the task set can still discriminate. MODEL With every case at 100%, the set is saturated: a regression of a few percent would not show. The cases are invented, hand-picked and in a public repository.
  4. Whether the grader is sound and who ran the eval. BOTH The graders have a failing run per check and were probed by independent model reviewers, but no human labelled a sample, and the same author directed the build and the runs.

What the data supports at most. On Claude Code 2.1.330, in these fixtures and this permission mode, milestones 0.3.2 passed every one of the 30 trials of its 10 cases. Whether the skill works for real users in other setups is a wider claim, and these trials do not settle it.

Appendix: run it yourself, exercises

This appendix is an addition to the structure above, for students who want to touch the harnesses.

Cost and safety first. A real run makes model calls on your account (about $0.04 to $0.25 per trial in these runs; agent-md-audit also fetches web pages). It needs Claude Code installed and logged in, and it must run outside the Claude Code Bash sandbox. For the git plugins the agent runs with a broad git grant in a temporary directory against a local bare remote; if your Bash is not sandboxed it runs with your user rights, so use a VM or container if that worries you. Recorded traces can contain your own ~/.claude/CLAUDE.md: do not share artifacts/ without looking.

Free and offline (start here)

# everything: the shared module, then all six harnesses (several minutes: three of them run real git)
make -C evals/_common test-all

# one harness
make -C evals/milestones test

# re-grade recorded runs without any model call (needs an artifacts/ directory from a real run of your own)
python3 evals/sitrep/python/run_evals.py --fixtures evals/sitrep/artifacts

Offline tests need Python 3 and make, nothing else (standard library only). Read a check in python/checks.py, then its entry in tests/test_checks.py.

Real runs (costs money)

# one case, one trial: always start here
make -C evals/block-force-push eval ARGS="--only plain-push-control --trials 1"

# several trials of several cases (comma separated, not a repeated flag)
make -C evals/milestones eval ARGS="--only create-tracker,update-finish-and-start --trials 3"

Each README names a canary case to run first. A trial that cannot run properly ends INCONCLUSIVE with the reason in the failures list.

Exercises

None of these needs a model.

1. Break a check on purpose (stage 4)

Pick one check in evals/milestones/python/checks.py and make it always return True. Which test fails, and why does that test exist? Revert.

2. Add a failing run (judge step 2)

Find a check whose entry in MUTATIONS covers only one way to fail. Write a second invented bad run that it should also catch. Does it? If not, you found a false negative.

3. Design a negative control (stage 2)

For sitrep, write a prompt close to "show me the situation" that must not trigger the skill. Why is a near miss a better test than an unrelated prompt?

4. Explain INCONCLUSIVE (stage 4)

Read the EXPLAINED_BY table in a harness. Give one example where a failed precondition should turn a failure into INCONCLUSIVE and one where it must not. State the rule in one sentence and test it on your examples.

5. Fair or unfair? (judge step 6)

Take the advisory reply-hands-over check of sitrep. Write a reply it would wrongly warn about and one it would wrongly accept. Why is it advisory instead of tuned?

6. Put an interval on a claim (stage 5)

A case passes 5 of 5 trials. Compute the one-sided 95% upper bound on its failure rate. How many clean trials would you need to rule out a 10% failure rate?

7. Review a harness (rule 2 and rule 6)

Pick one README and list every statement marked "unconfirmed". For each, say what real run or probe would settle it and what it would cost.
