Evals for agent skills and plugins

How do you know that an AI agent still does what a skill promises after you edit it? You cannot reread your way to the answer. You run the agent on fixed prompts and grade what it did. This document explains how the six eval harnesses of this repository work, what they found when they ran against a live agent, and what you can learn from them.

The one-paragraph version. Each harness builds a throwaway workspace, runs the real agent headless on a fixed prompt, and then grades the state the agent left behind (files, git history, a bare remote, a tracker, a report) with small pure functions. The agent's own account of what it did is only secondary evidence. A trial ends PASS, FAIL or INCONCLUSIVE (the behaviour under test never happened), and checks that only read the model's prose can warn but never decide. Every check has an invented failing run that a test enforces, so the machinery is tested offline for free before it ever spends a cent.

1. Why evals, and why not just unit tests

A skill is a text file of instructions that a language model reads. Changing one sentence can change behaviour in ways a diff does not show. Classic unit tests assume a deterministic function; here the "function" is a model that answers differently each time and that chooses its own tool calls. An eval is a repeatable experiment: fixed prompts, a controlled workspace, recorded behaviour, and explicit success criteria.

This repository already has ordinary unit tests under tests/. They feed invented input to the scripts of the plugins (the hook shell scripts, milestones.py). They cannot tell you whether a hook fires in a real session, whether the agent obeys what the hook says, or whether a skill triggers on the right sentence and stays quiet on the wrong one. The evals in evals/ answer exactly those questions, and they deliberately do not repeat what tests/ already checks.

Why not the built-in claude plugin eval? It is a good fit for "does the skill trigger and what does the reply say". These harnesses need three things its documentation did not offer when this was checked (see sources): assertions about file and git state (hashes, line counts, "nothing was committed"), a scripted second turn (the approval message after a proposal), and grading recorded runs offline so that the graders themselves can be unit-tested without model calls.

2. Skills, plugins and hooks in two minutes

Skill
A SKILL.md file with a short description. The agent loads the skill when the description matches what the user asked. The description drives triggering; the body is the behaviour.
Plugin
A package that can hold skills, hooks and scripts. This repository is a marketplace of six plugins: oaat, sitrep, milestones, agent-md-audit, auto-commit, block-force-push.
Hook
A script that Claude Code runs at an event, not the model. A Stop hook runs when the agent wants to finish; if it exits with code 2, its message goes back to the agent and the agent continues. A PreToolUse hook runs before a tool call; exit code 2 blocks the call and the agent sees the reason. Three of the plugins are hooks (auto-commit, block-force-push, and the reminder of milestones).
Headless run
claude -p "prompt" runs the agent without a terminal UI. With --output-format stream-json --verbose it prints one JSON event per line (the trace). The harnesses parse that trace.

3. Seven design ideas (and the reason for each)

  1. The workspace is the ground truth, the transcript is secondary. A transcript can only claim "I changed nothing". The harness snapshots the files (sha-256, line count, text), the git HEAD, and for the git plugins the bare remote, before and after each turn, and compares. The trace also misses work done by sub-agents; the files do not.
  2. Checks are pure functions. A check receives the recorded trace and the snapshots and returns (id, passed, note). No network, no model, no clock. That is what makes them testable.
  3. Every check has an invented failing run. A registry called MUTATIONS maps each check id to a doctored good run that must make exactly that check fail, and a test fails if a check has no entry. A check that has never been seen to fail proves nothing.
  4. Three verdicts, not two. If a precondition fails (the plugin did not load, the hook errored before it ran, the command was denied, the run crashed), the trial is INCONCLUSIVE, not a failure of the plugin. The rule is narrow: a precondition may explain a missing effect, never a wrong write. A denied call that left everything unchanged is inconclusive; a rewritten remote after the hook did run is still a FAIL.
  5. Deciding checks versus advisory ones. A check decided by state or by structured trace facts (tool name, command arguments, exit status) decides the verdict. A check that only matches words in text the model wrote is placed in a soft group: it is computed and reported as WARN but never changes the verdict. Regexes over prose cannot be made both unevadable and free of false alarms; three review rounds proved it.
  6. An offline stub agent. A small program prints invented traces and edits real files in real temporary git repositories, so the whole runner (build workspace, snapshots, grading, report) runs in the unit tests with no model. Recorded real runs can also be re-graded offline (--fixtures).
  7. Fixtures are built in code, never committed as files. A CLAUDE.md or .claude/ directory committed under evals/ would load for anyone working in the repository and would be audited by the skill under test. A test enforces that none exists.

4. Anatomy of one trial

Details that matter:

  • Isolation. The agent runs with --setting-sources project,local so your own user settings, hooks and plugins stay out, and with --plugin-dir pointing at the plugin under test. Variables such as CLAUDE_PROJECT_DIR are unset for the child, so a hook cannot look at the repository the harness was started from.
  • Approval by content. The second turn of a two-turn case states decisions by what they say ("drop the typecheck rule, leave AGENTS.md exactly as it is"), because the model numbers its proposals differently each run.
  • Which checks run depends on the case's expect column (for example proposal, apply, none for negative controls).
  • Cost. The result event of a resumed turn already reports the whole session's cost, so the shared reader takes the last result event rather than summing (see lessons).

The number of checks is the size of the harness's GROUPS registry; oaat has 12 checks per prompt (132 over its 11 prompts).

oaat — the teaching sample

A skill that presents exactly one pending item in a fixed shape and waits. Developed as the PA015 sample (05-oaat-skill-evals) and ported here.

Groups: outcome, process, style, efficiency. Prompts are explicit, implicit, contextual, follow-up (skip, stop, tangent) and negative controls. An optional second model call grades a JSON rubric for what code cannot judge.

agent-md-audit

A skill that audits CLAUDE.md and AGENTS.md against current documentation, proposes fixes, and applies them only after approval.

Graded: researched online before reading, proposed with a numbered table, changed no file before approval; after approval, the dead import and emphasis spam are gone, the contradiction is resolved, AGENTS.md is byte-identical, nothing is committed. The planted fixture has 229 lines and five defects.

auto-commit (Stop hook)

When the agent stops with an unsaved repository, the hook reports the state and the agent should save it.

Graded from git state: WIP committed and pushed to a local bare remote, remote changes merged (never rebased) with all earlier commits kept, .env in no commit, no remote invented, nothing done when the tree is clean. The prompts never mention git, so the outcome can only come from the hook.

block-force-push (PreToolUse hook)

The hook blocks a history rewrite. A small harness: three cases.

Graded: the rewrite is blocked, the remote ref is unchanged, the agent does not try another spelling, and an ordinary push still goes through (the control case). A hook that errors before running makes the trial INCONCLUSIVE.

milestones (skill + Stop reminder)

A project tracker in .cache/milestones.json written through a script.

Graded: the skill triggers on the right prompts and not on others; the tracker ends valid against its schema, in the requested state, other items untouched; it is written only through the script and never committed; the Stop reminder leads to an update only when a milestone really finished.

sitrep (skill)

Builds a temporary HTML situation report in a temp directory outside the project.

Graded: the skill triggers; data.js defines window.SITREP and validates against the schema offline in pure Python; the planted open items and their dependency are in the data; nothing is written into the project; the report directory is deleted afterwards.

6. What the real runs taught us

The interesting part of an eval project is what you only learn by running it. Everything here was measured on 22 November 2026 and is recorded in the READMEs of the harnesses.

Lesson 1: the environment can fail instead of the plugin. The first attempt ran inside the Claude Code Bash sandbox. Claude Code could not create its plugin data directory, so every hook errored with EPERM, and a session could not be resumed. The harness had graded one such trial as a FAIL of the plugin. That is wrong, and it is why the INCONCLUSIVE verdict and the hook-error precondition exist. Real runs must be started outside that sandbox.

Lesson 2: permission modes have surprising edges. Probing the real CLI with tiny calls showed that dontAsk denies any output redirect (printf x >> f), heredoc writes, shell-variable calls (S=…; python3 "$S" …) and reads of absolute paths outside the working directories, even when the command is on the allow-list. acceptEdits allows redirects; --add-dir allows the extra read. Plain pipes, ; chains, 2>/dev/null and multi-line commit messages were fine. Guessing grants twice failed; a handful of small probes settled it.

Lesson 3: an eval found a real flaw in a skill, and the fix could be measured. The milestones skill's script call was often rewritten by the model into a shell-variable form that no permission pattern can match.

  • Before any change: update-finish-and-start 0 of 3 and create-tracker 0 of 3 trials passed (all inconclusive or failed on the denial).
  • After asking in SKILL.md to write the script path out in every command: update 3 of 3; create-tracker still 1 of 3.
  • After adding a worked example of a chained create: create-tracker 3 of 3, then 3 of 3 again in the repeat pass.

The plugin was bumped twice (0.3.1, 0.3.2) because the behaviour visible to users changed.

Lesson 4: a vague prompt exposed a gap in a skill. With a milestone tracker present and the prompt "what is the state of things in this project?", the sitrep agent built its report from the tracker alone and never opened docs/open-questions.md, in 4 of 5 trials. Naming the file in the prompt made the case pass 5 of 5 but hid the gap, so the case was kept for what it tests (milestone integration) and a new case with the vague prompt was added. After SKILL.md step 1 was changed to tell the agent to look in the working tree, that case passed in every valid trial.

Lesson 5: a text check cannot be both strict and fair. Reviewers kept finding replies a regex graded wrongly in both directions (a correct reply failing, a lying reply passing) and each fix traded one error for the other. The structural answer was the soft group: prose checks warn, state decides.

Lesson 6: measure the instrument too. Two older harnesses summed the cost over every result event. In a real two-turn trace the first result reported $0.0906 and the second, of the same session, $0.1201, so the cumulative figure is the last one ($0.1201, not $0.2107). One fix in the shared module corrected both, and some figures quoted in the oaat README dropped (for example $0.76 to $0.64). The same project moved six copies of two files into one shared module, with a test that fails if a copy comes back.

The harnesses themselves were built by a pipeline of models in assigned roles (research, plan, build, adversarial review, fix), and an independent reviewer read the code on disk after each build. Across the four newer harnesses that review found real bugs over several rounds: checks that failed correct runs, checks that passed lying ones, and verdict logic that could turn a real failure into INCONCLUSIVE. It is a useful reminder that evals are software and need review and tests like any other.

7. How to run them

Cost and safety first. A real run makes model calls on your account (about $0.04 to $0.25 per trial in these runs; agent-md-audit also makes web fetches). It needs Claude Code installed and logged in. For the git plugins the agent runs with a broad git grant in a temporary directory against a local bare remote; if your Bash is not sandboxed it runs with your user rights, so use a VM or container if that worries you. Recorded traces can contain the contents of your ~/.claude/CLAUDE.md: do not share artifacts/ without looking.

Free and offline (start here)

# everything: shared module, then all six harnesses (a few minutes: three of them run real git)
make -C evals/_common test-all

# one harness
make -C evals/milestones test

# re-grade recorded runs without any model call (needs an artifacts/ directory from a real run of your own)
python3 evals/sitrep/python/run_evals.py --fixtures evals/sitrep/artifacts

Offline tests need Python 3 and make, nothing else (standard library only). They are the right place to learn the machinery: read a check in python/checks.py, then its entry in tests/test_checks.py.

Real runs (costs money)

# one case, one trial: always start here
make -C evals/block-force-push eval ARGS="--only plain-push-control --trials 1"

# several trials of several cases (comma separated, not a repeated flag)
make -C evals/milestones eval ARGS="--only create-tracker,update-finish-and-start --trials 3"

Run real trials from a normal terminal, outside the Claude Code Bash sandbox. A trial that cannot run properly ends INCONCLUSIVE with the reason in the failures list. Each README names a canary case to run first.

9. Exercises

Start with the offline tests; none of these needs a model.

1. Break a check on purpose

Pick one check in evals/milestones/python/checks.py and make it always return True. Which test fails, and why does that test exist? Revert.

2. Add a mutation

Find a check whose entry in MUTATIONS only covers one way to fail. Write a second invented bad run that it should also catch. Does it? If not, you found a false negative.

3. Design a negative control

For sitrep, write a prompt that is close to "show me the situation" but must not trigger the skill. Why is a near miss a better test than an obviously unrelated prompt?

4. Explain INCONCLUSIVE

Read the EXPLAINED_BY table in a harness. Give one example where a failed precondition should turn a failure into INCONCLUSIVE and one where it must not. State the rule in one sentence ("a precondition may explain a missing effect, never a wrong write") and test it on your examples.

5. Fair or unfair?

Take the advisory reply-hands-over check of sitrep. Write a reply it would wrongly warn about and one it would wrongly accept. Why was it made advisory instead of being tuned?

6. Plan an experiment

You change one sentence of a skill. How many trials per case do you need before you trust a before/after difference? What would you record to make the comparison fair? (Hint: in this project one case went from no passing trial to 3 of 3 after a short change to a skill.)

7. Review a harness

Pick one README and list every statement of the form "unconfirmed". For each, say what real run or probe would settle it, and what it would cost.

10. What is not measured

  • Sample sizes are small. One to five trials per case. Three clean trials do not prove a model never misses; they rule out frequent misses.
  • One model and one version of the tool. Everything was run on Claude Code 2.1.330. Hook and permission behaviour is documented in the READMEs as "confirmed" only for that version.
  • Heuristics remain. The command-line checks read parsed arguments, but a rare spelling (for example a push hidden inside a heredoc) can slip past them; the state checks still catch the result if it lands.
  • The checks judge structure, not quality. They can say a proposal named the planted defect, not whether the proposed fix is a good one.
  • The sandbox caveat. Real runs happen outside the Claude Code Bash sandbox; the graders and the unit tests do not need that.

11. Glossary and sources

Trace
The JSON-lines event stream of a headless run: init event, assistant and tool events, hook events, result event.
Snapshot
Every file with its hash, line count and text, plus git HEAD and, where relevant, the remote's refs. Taken before, after turn 1 and after turn 2.
Fixture
The prepared workspace a case starts from, generated by code in a temporary directory.
Negative control
A prompt on which the skill must not trigger or must change nothing.
Canary
The cheapest case that shows within one run whether the unverified assumptions hold.
Mutation (here)
An invented bad run, built by changing a good one, that a specific check must catch.
Precondition / soft check
See sections 3 and 5.
Flakiness
The same case giving different verdicts on identical input, measured by repeated trials.
