# Evals of the `sitrep` plugin

Run the skill on fixed prompts in throwaway directories and grade what it left behind. The files are the ground truth: the skill promises a temporary HTML report outside the project, made and removed by `report.sh`, with `index.html` untouched and nothing written into the repository. A transcript can only claim that, so every run snapshots the workspace and the report directory after each turn.

**Status: offline part verified, first real runs done.** The unit tests (`make -C evals/sitrep test`, 251 tests) exercise the checks on invented traces and the runner against a stub agent that runs the plugin's real `report.sh` in real temporary directories. Real runs of all 7 cases were made on 2026-11-22 under Claude Code 2.1.330: **6 PASS** (`explicit-report`, `implicit-big-picture`, `feedback-paste`, `negative-plain-list`, `negative-code`, `negative-clean-tree`) and `with-milestones` **FAIL**, graded before the fix described below (total cost about $0.7; regrading the recorded traces offline reads $0.53 from the last result event of each trial). That FAIL was a harness defect, not a finding about the skill: the agent chained `ls`, `cat`, `git log | head` into one Bash command, `git log` and `head` were not granted, `dontAsk` denied the whole line, and the agent (correctly) concluded Bash was denied, never ran `report.sh` and answered in text. The harness now grants those read-only helpers (see Permissions) and grades a trial with a denied Bash call in which `report.sh new` was never tried as **INCONCLUSIVE** (check `not-permission-blocked`, note naming the denied command); the recorded trace regrades as INCONCLUSIVE. `with-milestones` was re-run twice after the fix: **1 PASS, 1 FAIL**. The FAIL is a verdict about the skill, not the harness: the report held one item (the milestone item) and none of the five open items planted in `docs/open-questions.md`, so `dependency-recorded` failed (the advisory `items-cover-planted` showed 0 of 5). The skill's collect step says to gather open items from the files in scope; here the agent used the tracker only. One trial each way is too few to call it a rate: run `--only with-milestones --trials 5` before concluding.

**Real runs must be run OUTSIDE the Claude Code Bash sandbox.** Inside it Claude Code cannot create `~/.claude/plugins/data/<name>-inline` nor write `~/.claude/projects`, so hooks error with EPERM and `--resume` fails with "No conversation found". The harness reports such runs as INCONCLUSIVE (`run-completed` / `skill-loaded`), never as a result about the skill.

**What decides and what only warns.** A check that is decided by workspace state or by structured trace facts (tool name, the argv of a Bash command, a result subtype, the files in the report directory, the parsed `data.js` structure) decides the verdict. A check that rests only on matching words in text the model wrote (the reply, the wording of item titles and of the current milestone) is **advisory**: group `soft`, reported as **WARN** with its note, never part of the verdict or the exit code. Three review rounds showed that such a regex cannot be made both non-evadable and free of false positives.

The plugin has no unit tests of its own (its only code is a 30-line shell script), so `tests/test_plugin.py` also exercises `report.sh` once against a throwaway `TMPDIR`: `new`, `clean`, what `clean` refuses, the day-old sweep.

## Why not `claude plugin eval`

The CLI's own runner ([docs](https://code.claude.com/docs/en/plugin-evals.md), checked 2026-11-22 as reported by the planning research; not re-read while building) fits triggering and reply-text cases. This skill needs what it does not document:

- **State assertions.** No git-state or hash grader, so "`index.html` equals the template", "the report directory is gone" and "the tracker is byte-identical" cannot be asserted.
- **A custom grader.** The report's `data.js` must be parsed and checked against `schema.md`; no custom-code grader is documented.
- **Offline grading.** No grader replay is documented, so the graders could not be unit-tested without model calls.
- **A scripted second turn.** The cleanup turn needs a reply after the report exists; the documented route is replaying a saved transcript.

## The checks (`python/checks.py`)

26 checks in five groups (8 outcome, 6 gate, 4 process, 4 precondition, 4 soft). Commands are judged by their **parsed argv** (`python/shell_argv.py`: split at `;`, `&`, `&&`, `||`, `|`, newlines, parentheses; leading `VAR=` words and wrappers such as `env`, `sudo`, `xargs` skipped; `sh -c STRING` and `eval` parsed again, also with combined short flags such as `bash -lc`, `-ec`; `bash script.sh` read as a call of `script.sh`), never by text that merely mentions a command: `cat report.sh`, `grep mkdir notes.md`, `echo "rm -rf x"` and `git rm` flag nothing.

- **precondition:** `state-recorded` (the workspace snapshots the checks compare exist: `before` and `after1` for every case, plus the `TMPDIR` listing for the negative cases; the one after turn 2 belongs to `run-completed`. Missing means nothing was measured: a case that was never recorded, `--fixtures` on a directory without it, a trace without its `.state.json`, or a state file that is not readable JSON. The trial is INCONCLUSIVE, with a note naming what is missing, not FAIL: `project-untouched` and the checks that read the report are explained by it, while what the trace itself proves still stands, see the verdict); `run-completed` (every turn the case needs ended in a `success` result event that is not an error, the runner noted nothing such as a non-zero exit or a timeout, and the snapshot after turn 2 exists; the problems are kept per turn, see the verdict; without it a crashed run would pass every negative case, which only look for something absent); `report-located` (the harness found the report directory, from the path `report.sh new` printed, else a `sitrep.*` directory in the trial `TMPDIR`; it fails only when `report.sh new` was tried, or refused, and left nothing: a skill that never ran step 2 passes it and fails `created-by-script` instead); `not-permission-blocked` (no denied Bash call in turn 1 when `report.sh new` was never tried: a denied exploration command, e.g. a compound line with one ungranted part, ends the agent's work before the skill's own step, so the trial is INCONCLUSIVE and the note names the denied command; a denied unrelated call followed by a `report.sh new` that ran is fine. Read from `result.permission_denials`, from system `permission_denied` events and from a Bash `tool_result` that is not marked `is_error: false` and starts like `Permission to use Bash has been denied`; one call seen through several channels counts once. Also: no denial of a Bash call of `report.sh new` or `report.sh clean`, or of a Write or Edit whose `file_path` is a `data.js`; read from `result.permission_denials`, from system `permission_denied` events and from the `tool_result` text of such a call when it reads like a refusal: `permission`, `denied`, `not allowed`, `not granted`, `disallowed`, `requires approval`, `not permitted`. The result of a Write or Edit that starts with `The file ` or `File created successfully`, or that echoes a `cat -n` snippet, is not read, because it may quote item text such as "waiting for permission from legal"; the rest of a Write or Edit result is read up to 200 characters. A denial of any other command that merely names the script or the file, such as `node --check .../data.js` or `cat report.sh`, is not counted, nor are the expected denials of `open`, `xdg-open`, `start`, which are not granted; a denial element without `tool_name` and `tool_input` is read by its strings).
- **process:** `skill-loaded` (plugin listed and its skill among the init skills; exactly one plugin named `sitrep`, whose init `path` is the run's `--plugin-dir`, recorded as `plugin` in the state file; every `report.sh` call that names the script by an absolute or `~` path lies under that directory (a relative path after a `cd` is not judged: the init `path` tells the copies apart), so an installed copy is not graded as the working copy; a recording without `plugin` skips the path tests); `skill-trigger` (a Skill call exactly when the case says so); `created-by-script` (`report.sh new` ran, no `mkdir` or `mktemp` command, and no `report.sh clean` naming the directory in turn 1: removing the report before the user said they are done is a finding against the skill, and `report-located` then does not blame the environment for the missing directory); `cleaned-by-script` (turn 2 ran `report.sh clean` naming the directory, and the script did not answer `refusing to delete`; no removal command ran that names the directory or any `sitrep` path such as a `sitrep.*` glob: `rm`, `/bin/rm`, `rmdir`, `unlink`, `find ... -delete` or `-exec rm`, an interpreter given `rmtree`, also in a compound command or inside `sh -c`; an `rm` of something else in the same line does not count, a command fed by `xargs` is judged by the whole line).
- **gate:** `report-outside-project`; `project-untouched` (snapshot after every turn equals the one before: files, HEAD, `git status` minus the `?? .claude/` marker; a missing snapshot after turn 2 is not a write, `run-completed` reports the turn that did not run); `index-untouched` (sha256 equals the plugin's `template.html`); `only-data-added` (the directory holds exactly `index.html` and `data.js`); `tracker-untouched` (it also trips `project-untouched`, by design: it names the cause); `no-report-when-negative` (no `sitrep.*` in the trial `TMPDIR`, no call of `report.sh` and no report-like file added to the workspace: a name ending in `.html` or `.htm`, `data.js`, or containing `sitrep`; other edits are allowed, `negative-code` edits `src/textutil.py`).
- **outcome** (the parsed structure of `data.js` and the files): `data-defines-sitrep`, `data-parses`, `data-valid` (against `schema.md`), `dependency-recorded` (structure only: some item lists in `dependsOn` a different item that exists), `start-here-set`, `milestone-item` (item `ms-3`: `blocker`, `blocked`, urgency 3), `milestone-strip` (the strip says done 1 of total 4; the numbers only), `report-cleaned`.
- **soft (advisory, WARN):** `reply-hands-over` (the reply names the `sitrep.XXXXXX` directory of the recorded report, mentions Copy JSON, has at most 4 list lines, at most 1500 characters, and at most 4 units, a unit being a line or a sentence, that name a planted topic or an item title of `data.js`; a period after `vs.`, `e.g.`, `i.e.`, `etc.` does not end a sentence; the two or three lines SKILL.md step 3 asks for pass, a table row, a bold line or a sentence per item is a unit each, so pasting all five items warns; a list pasted into one run-on line under 1500 characters does not warn, and the 1500 and the 4 are guesses); `items-cover-planted` (five distinct items, one per planted keyword, assigned one-to-one: a keyword that only appears in another item's detail does not count; the skill may merge items, so a merge warns although it behaves well); `dependency-direction` (a migration item lists a different database item in `dependsOn`, and that one does not list it back; roles come from the item titles first and only then from the details, a title naming both topics allows both roles, and an item with a neutral title whose detail names a database counts as the database item when a migration item depends on it); `milestone-current` (`milestones.current` contains "Storage layer").

Which checks run for which case: every case gets `run-completed` and `state-recorded`; `none` cases get `skill-loaded`, `skill-trigger` and `no-report-when-negative`; `feedback` gets `skill-loaded`, `skill-trigger` and `project-untouched`; report cases get every other check except `no-report-when-negative`, with the milestone and tracker checks only in `with-milestones` and the cleanup checks (`cleaned-by-script`, `report-cleaned`) only in `explicit-report`.

**Cases that were never recorded.** `run_evals.py --fixtures DIR` grades every case of the CSV, so a case with no trace in `DIR` (for example after one `make eval ARGS="--only explicit-report"`) is INCONCLUSIVE with `run-completed` and `state-recorded` failed, never FAIL: negative and positive cases get the same verdict for the same cause. Use `--only` to grade just the cases you recorded. A trace whose `.state.json` is missing or unreadable is INCONCLUSIVE too, unless the trace alone proves a finding (a Skill call in a negative case, a `report.sh` call in a negative case, no Skill call in a positive case whose turn 1 finished).

**Verdict.** A trial is PASS, FAIL or INCONCLUSIVE; exit code 1 for FAIL or INCONCLUSIVE, so a run that crashed is never green. Advisory checks are not part of it: a trial whose only failures are `soft` is a **PASS with warnings**, the report lists each warning with its note (`warn` column, `[WARN]` lines, `soft n/m` in the group counts, `WARN ... on N trial(s)` in the summary, `warnings` in `results.json`), and the exit code stays 0.

Among the hard checks, a failed precondition (`run-completed`, `state-recorded`, `report-located`, `not-permission-blocked`), or a plugin that did not load or is not the one under test (`skill-loaded`), means the behaviour was never exercised: INCONCLUSIVE, **but only for the failures the damaged turn can explain**. The damage is scoped by turn:

- *turn 1 damaged* (no success result, a runner note on it, a denied `report.sh` call or `data.js` write in it, the report it tried to make not found, the plugin not loaded, the snapshots not recorded) explains every failed check that reads what turn 1 left behind, and the cleanup checks too;
- *turn 2 damaged* (no success result, never ran, a denial in it) explains only `cleaned-by-script` and `report-cleaned`. A `data.js` without dependencies after a turn 1 that finished is a FAIL although turn 2 crashed;
- the runner's note belongs to turn 1 in a one-turn case or when turn 1 itself has a problem, otherwise to turn 2.

Some failures stand on their own whatever happened and make the trial FAIL: `project-untouched` (proven by snapshots, so only when `before` and `after1` were recorded: without them it is explained by `state-recorded`); `index-untouched` when `report.sh new` ran and the directory exists (the page was edited); `skill-trigger` when a Skill call exists in a case that should not trigger (positive evidence, even from a crashed run) or when no Skill call exists in a case that should trigger and turn 1 finished; `no-report-when-negative` when a report was made (a `sitrep.*` directory, a `report.sh` call, a report-like file) and the plugin did load.

By design a report made by hand after `report.sh new` failed (`mkdir` plus Write outside the `sitrep.*` glob) is INCONCLUSIVE, not FAIL: `report.sh` may have failed because of the environment (`${CLAUDE_SKILL_DIR}` unsubstituted: Unconfirmed item 6), `report-located` fails, and `created-by-script` lists the `mkdir` in its note. A `mkdir` next to a report that `report.sh` did make is a FAIL.

Every check has an invented failing run (`tests/test_checks.py`, `MUTATIONS`, one per check id; `MORE_MUTATIONS` holds further failing runs for the same checks: a reversed dependency, a link to an item that does not exist, `/bin/rm`, a refusal visible only in a tool result, a pasted table, a report cleaned in the turn that made it, a refused clean followed by `rm` on a glob, the real `with-milestones` shape (a compound exploration command denied, `report.sh new` never tried; built from invented text) in two channels, and so on; `DeniedExploration` holds that shape's verdict, the counter-case (a denied unrelated call followed by a `report.sh new` that ran stays PASS) and the de-duplication of one denial seen through three channels; `GoodVariants` holds runs that must PASS although they look wrong to a loose check, such as a denied `node --check .../data.js`, or read-only commands that mention `mkdir`, `rm` or `report.sh`), a test fails when a check has none, and each mutation must fail exactly its own check plus a cascade that is written down next to it (no report found, unparsed data, the tracker also being part of the project). `SoftChecks` shows that each advisory check, failing alone or all together, gives PASS with warnings, and that every hard mutation is not a PASS; `ScopedVerdict` holds the per-turn cases. Cost is read from the last result event of a trial, on the unconfirmed assumption (item 9 below) that a resumed session reports its whole cost there; `agent_trace.stats` sums over result events and would count turn 1 twice if so.

## A real run

- **Cost:** model calls on your own account; the first real runs of all 7 cases cost about $0.7 in total. Each call is capped at `--max-budget-usd 2`. `explicit-report` is two calls, the other six are one each. Start with one case, `--trials 1`, and read the cost from the result events: `explicit-report` first, because it exercises the whole life cycle.
- **Isolation:** every trial runs in a fresh temporary root: `ws` (the cwd, a git repo whose local config sets identity, no signing and an empty hooks directory), `tmp` (the child's `TMPDIR`, granted with `--add-dir`, so `report.sh` is meant to create and sweep `sitrep.*` only there: item 3 below), `hooks`. `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` point at nothing. `--setting-sources project,local` is meant to keep your user settings, hooks and plugins out (item 5 below), and `env -u` removes `CLAUDE_PROJECT_DIR`, `CLAUDE_HOOK_RUNNING` and the `MILESTONES_*` variables so that nothing looks at the repository the harness was started in. `--bare` is not used: `claude --help` says it skips hooks, plugin sync and more, and what that does to `--plugin-dir` has not been checked.
- **`with-milestones` and the vague prompt (a finding about the skill, not graded):** with the vague prompt "what's the state of things in this project right now?" the agent built the report from the milestone tracker alone and never opened `docs/open-questions.md` in 4 of 5 real trials (the fifth passed), although SKILL.md step 1 says to gather open items from "files in scope". The case now names the file in its prompt, so that it tests what it is for (milestone items and the progress strip folded into the report) and not file discovery. If you want the skill to discover such files on its own, SKILL.md step 1 would have to say so (for example: look for notes and open-question documents in the working tree); that is a plugin change this harness does not make.
- **Permission mode and directories:** `--permission-mode acceptEdits`, not `dontAsk`, and `--add-dir` for the trial `TMPDIR` **and the plugin directory**. Probes of the real CLI (2026-11-22, Claude Code 2.1.330) showed that `dontAsk` denies a heredoc write (`cat > data.js <<EOF`, which the agent used in a real trial) and a Bash read of an absolute path outside the working directories (`cat <plugin>/skills/sitrep/schema.md`, which the skill itself asks for) unless that directory is added; stderr redirects (`2>/dev/null`, `2>&1`) and pipes are fine. Both denials made the agent give up on Bash in 3 of 5 `with-milestones` trials (INCONCLUSIVE; the other 2 trials passed).
- **Permissions, stated plainly:** `Write` and `Edit` are granted on purpose, so a write into the project can happen and be measured. The granted Bash commands are `report.sh` (two spellings, because SKILL.md puts the closing quote of the script path before the verb) and the read-only helpers an agent chains while it looks around: `ls`, `cat`, `git log`, `git status`, `git diff`, `head`, `tail`, `wc`, `grep`, `find`, each with and without arguments (`run_evals.READ_ONLY_BASH`; a test pins the list and that nothing that writes or runs code, such as `sed`, `tee`, `xargs`, `sh`, `python`, bare `git`, `env`, `rm`, is granted). Two things a Bash pattern cannot express: `find` can still be given `-delete` or `-exec`, and `git log`/`git diff` accept `--output=FILE`; the workspace is a throwaway repository and `project-untouched` would show a write there, but a command with an absolute path could reach further. `open`, `xdg-open` and `start` are not granted, which keeps a browser window from opening (`dontAsk` denies an ungranted Bash command: confirmed in the first real run). A compound command is denied as a whole when any part is ungranted. If headless Bash turns out to be unsandboxed, those commands run with your user's rights, with a temporary directory as cwd.
- **Artifacts** (`artifacts/`, git-ignored: traces, state snapshots with the runner's note, `results.json`; `--fixtures` grades a recorded run with that note, so a non-zero exit after a success result stays INCONCLUSIVE) may contain whatever your own user-level memory put into the session: review before sharing.
- **First things to check when a real run fails or is inconclusive:**
  1. INCONCLUSIVE on every report case: read the "Unconfirmed" list, items 1 to 3 first; and check that the run was made outside the Claude Code Bash sandbox (see Status). An INCONCLUSIVE `not-permission-blocked` that names a denied command that is not `report.sh`: grant it in `ALLOWED` if it is read-only and the agent naturally chains it.
  2. `feedback-paste` may fail `project-untouched` although the behaviour is good: SKILL.md step 4 says to apply decisions the agent can apply, and "go with Postgres" may be written into `docs/open-questions.md`. If so, narrow the check, not the skill.
  3. `items-cover-planted` and `dependency-direction` match keywords and are advisory (WARN), by design and not a gap to close: a run that keeps only the database and migration items, with their `dependsOn` link, and drops the other three planted items is a PASS with a WARN, because the skill may merge or drop items and a word match cannot tell a merge from a loss: the skill allows merging items, so a model that merges the database decision with the migration blocker warns while behaving well. Read the note, do not loosen the verdict.
  4. `reply-hands-over` is a text check on one reply, advisory too; read the reply before believing a warning.
  5. `implicit-big-picture` and `with-milestones` do not name `docs/open-questions.md`; the fixture README points to it, but the agent may not read it.
- **Timeout:** 300 s per model call.

## Limits of the readers

`shell_argv.py` is a small tokenizer over `shlex`, not a shell: it does not expand variables, globs or `$(...)` (the inner command is read as a command of its own), does not follow aliases, functions, `cd`, here-documents or a script that a command writes and then runs, and reads a quoted `;`, `|` or `&` as an operator. A line with an unbalanced quote is read again with its quote characters blanked. A removal or a directory made through a program the reader does not know (for example `python3 script.py` that calls `rmtree` inside the file) is not seen; the state checks (`report-cleaned`, the report directory, the workspace snapshots) still are.

`data.js` is read by a small pure-Python reader (`python/sitrep_data.py`); no JavaScript is ever executed, no `node`. It reads what data files use: comments, bare keys, single, double and backtick strings with escapes, trailing commas, numbers, `true`/`false`/`null`. Only comments and a `"use strict"` directive may come before `window.SITREP =`: any other statement before it (an `import`, a call, a variable) fails `data-parses`, as a browser may reject it. It does not read expressions: string concatenation, variables, function calls, spreads, computed keys, `${}` in template strings. A valid-looking file that uses them fails `data-parses` with the reason in the note, although a browser would run it. The validator follows `schema.md` and is stricter in one place: every item needs a unique string `id` (`schema.md` calls only the titles essential, but `dependsOn`, stable regeneration and the feedback export are keyed by it).

## Confirmed by the first real runs, and still unconfirmed

**Confirmed** (7 real runs, Claude Code 2.1.330, 2026-11-22):

- the skill triggers on the explicit and the implicit prompt and on the pasted feedback, and does not trigger on the three negative cases;
- `report.sh` runs and cleans up under `--add-dir TMPDIR` (the report is made in the trial `TMPDIR`, and `report.sh clean` removes it in the second turn);
- the two-turn `--resume` works (run outside the Claude Code Bash sandbox);
- `--permission-mode dontAsk` denies an ungranted Bash command, as a whole when it is a compound line; the denial appears both as a system `permission_denied` event and in `result.permission_denials` (an element with `tool_name`, `tool_use_id`, `tool_input` as an object) and as a Bash `tool_result` with `is_error: true` reading `Permission to use Bash has been denied because Claude Code is running in don't ask mode`; the agent reports the denial and does not work around it.

**Unconfirmed**, the rest of what the design leans on (items renumbered; the checks and notes above refer to these numbers):

1. Whether a `Write` into a directory outside the cwd is allowed with a bare `Write` grant plus `--add-dir` in a headless `dontAsk` run. If it is refused and the refusal is recorded (in `permission_denials`, in a `permission_denied` event, or as `tool_result` text that reads as a refusal: the wording is a guess for Write and Edit, matched on the words listed under the checks), `not-permission-blocked` fails: INCONCLUSIVE. A refusal that is recorded in none of these shows up as a FAIL of the data checks, blaming the skill for the sandbox.
2. Whether `Bash(*report.sh *)` and `Bash(*report.sh" *)` match every spelling of a command that starts with a quoted absolute path (the real runs ran `report.sh` under these grants; `test_plugin` models `*` as "anything"). Fallback: an `--agent-cmd` with the absolute script path in the rule.
3. Whether headless Bash is sandboxed on this machine and which `TMPDIR` the Bash tool sees on every setup; the real runs found the report in the child's `TMPDIR`.
4. Whether `Bash(head *)` also matches a bare `head` (hence the bare grants), and the shape of Bash `tool_result` lists of text blocks (both a string and a list are read).
5. The Skill input field (`skill`) and the spelling `plugin:skill` in init `skills[]` and `<name>@inline` in `plugins[]` are seen in recorded traces; that the init `path` equals `--plugin-dir` for `sitrep` and that `--setting-sources project,local` keeps an installed `sitrep` and user hooks out of the run is not separately verified.
6. Whether `${CLAUDE_SKILL_DIR}` is substituted in the skill text in every headless run (it was in the real runs that executed `report.sh`).
7. The element shape of `result.permission_denials` for tools other than Bash (a Write or Edit): read by `tool_name` and `tool_input` when both are there, otherwise by the element's strings. A denial whose only text is a sentence that mentions `data.js` is not counted.
8. Whether headless runs create `.claude/.cc-writes` in the workspace: ignored by the snapshot, and `?? .claude/` is dropped from the status.
9. Whether a resumed session's result event reports the cost of the whole session (the cost is read from the last result event on that assumption; the $0.53 regraded against about $0.7 observed suggests the question is open).
10. Whether `--resume` gives the model the report path in every case (it did in the real `explicit-report` run); if the session id cannot be read, the run is reported with a note and the cleanup checks fail.
11. Whether setting `TMPDIR` for the child changes where Claude Code itself keeps scratch files.
