# Evals of the `milestones` plugin

Run the plugin on fixed prompts in throwaway git repositories and grade what it left behind. The ground truth is the workspace and its git state (the tracker file, `HEAD`, which paths git ever held, which files changed); the transcript is secondary evidence, because it shows only the main conversation.

**Status: the offline part is verified, the real run was never executed.** The unit tests (224) exercise the checks on invented traces and the whole runner against a stub agent in real temporary git repositories. Nobody has run `make eval` against a live `claude`: every fact in "Unconfirmed" below is open until the first real run, and the regex checks may need loosening after the first real trace.

## What this adds to `tests/milestones/`

`tests/milestones/` (68 tests) covers the script, the schema-vs-validator agreement, the statusline and the reminder script's firing conditions, all with invented payloads and no model. The evals add what only a live session shows:

1. the skill **triggers** on the description's phrasings and not on near misses;
2. the agent **translates a sentence into tracker state** (ids, states, `needs`) and the file ends valid against the plugin's schema;
3. it writes the tracker **only through `milestones.py`**, never with Edit/Write or a shell redirect, and never commits it;
4. in a real session the **Stop reminder** leads to an update when a milestone did finish and to no change when nothing happened.

The statusline is not evaluated: it is a user setting with no model behaviour.

## Why not `claude plugin eval`

Docs ([code.claude.com/docs/en/plugin-evals.md](https://code.claude.com/docs/en/plugin-evals.md), checked 2026-11-22 **as reported by the research that planned this harness; not re-read when it was built**) are reported to lack: a git-state or hash grader (so "the tracker is byte-identical", "nothing was committed" and "no stray file" cannot be asserted), a custom-code grader (the schema check, the `started`/`finished`/`updated` bookkeeping and the tri-state verdict are code), and offline grading (the graders could not be unit-tested without model calls). A scripted second turn, the fourth gap the sibling harnesses cite, does not matter here: every case is one turn.

| `show-where-are-we` | tracker | show | implicit trigger on "where are we"; `show` is read-only; the reply names the milestone in progress |
| `show-progress-bar` | tracker | show | the shortest trigger phrase of the description |
| `update-finish-and-start` | tracker | update, `2=done,3=doing` | a sentence becomes state, through the script, with `finished`/`started` written |
| `update-blocked-needs-you` | tracker | update, `4=blocked,4.needs=you` | blocked plus `needs` that is exactly `you` or `author` (case aside; not `me`, `user`, `you (...)` or `legal`: the plugin's `is_you()` sets the statusline flag for those two words only), the field behind the statusline flag |
| `create-tracker` | bare | create, `title=Importer,count=3,names=...` | starting a tracker with `init --empty`/`title`/`add` rather than writing JSON |

| `negative-explain` | bare | none | the word "milestone" alone must not trigger |
| `negative-github` | bare | none | near miss: milestones of another system (`gh`) |
| `reminder-nothing-changed` | stale-idle | reminded-quiet | "if nothing changed, do nothing": the reminder must not provoke an invented update |

Fixtures are built in code (`python/fixtures.py`) in a temporary directory, never stored: a committed `.cache/milestones.json` under `evals/` would be read by the plugin's own hook and statusline, a `CLAUDE.md` or `.claude/` by Claude Code, for anyone working in this repository. A test walks this directory and fails if one is there.

- `bare`: `README.md`, `src/textutil.py` (one function) and a `.gitignore` holding `.cache/`; no tracker.
- `tracker`: bare plus a tracker, "To release 1.0": 1 Schema design done, 2 Storage layer doing (started 3 h ago), 3 Sync API todo, 4 Release sign-off todo.
- `stale-task`: a tracker whose item 2 is "Add slugify to textutil", doing.
- `stale-idle`: the `tracker` fixture again.

Both stale fixtures get their tracker mtime set two hours back with `os.utime` **after** the fixture commit, so the commit is newer than the tracker (the hook's activity condition). Staleness therefore comes from the mtime, not from `MILESTONES_STALE_MINUTES`. A test runs the real `milestones-reminder.sh` on the fixtures (when `jq` is installed): it exits 2 on both stale ones and 0 on `tracker`.

The reminder prompts never mention git, commits, saving, milestones or a tracker, so an outcome can only come from the hook's report.

## The checks (`python/checks.py`)

Every check is a pure function of the case. Which ones apply depends on the case's `expect`. Five groups; **a check that rests only on parsing the model's own prose never decides a verdict** (three review rounds showed that a regex over free text cannot be both non-evadable and free of false positives), so it lives in the advisory group `soft`. Everything else is decided by the workspace and git state or by structured trace facts (tool name, parsed command argv, tool_result status).

- **precondition** (a failure makes the trial **INCONCLUSIVE**, unless a failed hard check is not explained by it, see Verdict): `agent-completed` (runs in **every** case: no run note such as a non-zero exit or a timeout, a result event that is present, has subtype `success` and no `is_error`, and both snapshots present with files; without it a run that died after the init event passes every negative case, because it leaves the files untouched. The reply text is **not** a condition: the Stop hook asks for a silent update, so an empty last turn is a correct run, and demanding text would hide a real failure behind INCONCLUSIVE); `plugin-under-test-isolated` (runs in **every** case: `plugins[]` of system/init holds at most one entry named `milestones`, the `--plugin-dir` copy; an installed copy, alone or beside the inline one, or a duplicate is an environment leak. No entry at all passes here and fails `skill-loaded`); `not-permission-blocked` (runs in **every** case that can call the script: show, update, create, both reminder cases and the negatives. A call to `milestones.py` is **denied** when an element of `permission_denials` (or a system `permission_denied` event) carries its `tool_use_id`, whatever else the element holds, or when its own tool_result has `is_error` and reads like a denial. An element without a usable id is matched to such a call with the same arguments, else by its `tool_input` or whole text. A denied call is cleared only by a later identical call (path and quotes aside) whose tool_result has no `is_error` and does not read like a denial; for an unmatched element the successful-looking calls must outnumber the unmatched elements, so a denial whose own result lacks `is_error` does not clear itself. The shapes are unconfirmed: this degrades toward INCONCLUSIVE, never toward a silent pass); `reminder-fired` (the marker `.cache/.milestones-reminded` exists after and not before: proof the plugin's hook ran); `reminder-delivered` (the hook's report is **in the conversation** (a user, assistant or result event), **or** the tracker changed, whatever the change; a Stop `hook_response` with exit code 2 and nothing else is not delivery).
- **process:** `skill-loaded` (system/init lists the skill and has a `milestones` entry in `plugins[]` that is the `--plugin-dir` copy: source `milestones@inline`, or a path equal to `--plugin`); `skill-trigger` (a Skill call for `milestones` exists exactly when the case says; not graded in the reminder cases); `shown-by-script` (a Bash command whose parsed argv runs `milestones.py show`, also with a quoted path, a `cd ... &&` prefix or `--json`, **and its tool_result holds the tracker's title and is not an error**); `written-by-script` (when the tracker changed, a Bash command ran `set`, `add`, `remove`, `title` or `init`). A call is recognised from the argv of a command segment: the command word is a Python interpreter (after env assignments, `env`, `time`, `nohup`) and a later token is a path ending `milestones.py`; text that only mentions the script (`echo`, `grep`, a `python3 -c` string) is not a call.
- **gate:** `show-reads-only` (tracker sha256 unchanged); `no-write-attempt` (show, `reminded-quiet` and `none` cases: no `milestones.py` write subcommand (`set`, `add`, `remove`, `title`, `init`) anywhere in the trace, **whatever came of it**: a denied or refused attempt leaves the tracker as it was, so the state alone cannot tell that the agent tried); `no-direct-tracker-write` (no Edit/Write/NotebookEdit/MultiEdit of a path ending `milestones.json`, and no Bash command segment that writes the file: the command line is split on unquoted `&&`, `||`, `;`, `|` and newlines, and a segment naming the tracker fails on a redirect into it, `tee`/`mv`/`rm`/`truncate`/`sponge`, `sed -i`/`--in-place`, `perl -i`/`-pi`, `awk -i inplace`, `dd of=`, `cp`/`install`/`ln` with the tracker as destination, or a Python `open(..., 'w')` (the mode must be a string inside that `open(` call, one level of nested parentheses allowed), `mode='w'`, `write_text`, `json.dump(` (not when it dumps to `sys.stdout`/`sys.stderr`), `shutil` or `os` file move. A file name that continues after `milestones.json` (`.bak`, `~`) is another file; `git rm --cached` only edits the index. A segment that runs the script is checked for a redirect only. Reads such as `cat`, `jq .title`, `perl -ne`, `json.dumps(json.load(open(...)))` or `json.dump(d, sys.stdout)` pass. A denied attempt still counts: the trace holds attempts); `tracker-not-committed` (no `.cache/` path in `git ls-files` or anywhere in `git log --all`, and, in the show, update, create and none cases, `HEAD` did not move: in the reminder cases an agent may legitimately commit its own edit); `nothing-else-changed` (no file added, removed or modified except the tracker and the hook's marker: **any other file under `.cache/` counts**; the code file `src/textutil.py` may change in `reminder-finishes` and in a `none` case on a tracker fixture); `no-tracker-when-negative` (no tracker appears on the bare fixture).
- **outcome:** `tracker-valid` (parses and passes `python/schema_check.py`, a standard-library validator driven by the plugin's `milestones.schema.json`, plus unique ids); `wanted-state` (the case's `want` ids, states and `needs`: `ID.needs=set` is any non-empty value, `ID.needs=you` must be exactly `you` or `author`, case aside, the plugin's own `is_you()` semantics, which a test compares against the script); `others-untouched` (items not named are equal to before; "named" are the ids in `want` states, `needs=set` and `needs=you`; items named keep their name; none removed or renumbered; same title); `timestamps-by-script` (an item that became doing has `started`, one that became done has `finished`, and the top-level `updated` was refreshed: bookkeeping only the script does); `tracker-created` (title, item count, and **each wanted name word in its own distinct item**: a maximum matching, so one item holding every word beside junk items fails); `quiet-when-nothing-changed` (no item's name, state, `left` or `needs` and not the title differs from before).
- **soft (advisory, WARN):** `reply-names-current` (the reply names the milestone in progress and does not say it is finished). This reads the model's prose only, so a failure is a **WARN**: computed, listed with its note under "warnings", counted separately, and it never changes the PASS/FAIL/INCONCLUSIVE verdict or the exit code. "Says finished" is: the name, then only blanks (never a newline), a copula (`is`, `was`, `has`, `has been`, `'s`), an adverb or a single `:`, dash, arrow, `|` or `(`, then finished, complete(d), done, shipped or wrapped up **ending the clause** (end of the line, punctuation other than `:`, `and`, `but`, `then`: "Done:" after a name is the label of the next item), or the name followed by a check mark (also after a colon), or finished/completed/shipped right before the name ("we finished the Storage layer"). A match in a clause that holds once, after, until, when, before, if, unless, while, not, never or yet is ignored. Sentence punctuation between name and verb breaks the link, and a verb followed by more words ("done so far", "done 1/4") is partial. Known limits: other phrasings, a hedge after the name ("done, apart from ..."), and a negation far from the verb.

A `none` case runs `agent-completed`, `plugin-under-test-isolated`, `skill-loaded`, `skill-trigger`, `not-permission-blocked`, `no-write-attempt`, `no-direct-tracker-write`, `tracker-not-committed` and `nothing-else-changed`, plus `show-reads-only` on a fixture that has a tracker (the prompt may edit `src/textutil.py`) or `no-tracker-when-negative` on `bare`. The branch comes from the row's fixture, never from the snapshots.

**Verdict.** Decided by the hard checks only (every group but `soft`):

- **PASS** when no hard check fails. Failed soft checks are WARNs: the trial is still PASS, the report lists them ("PASS with warnings"), the table has a WARN column and the summary counts them; the exit code is 0.
- **INCONCLUSIVE** when a precondition fails and **every** failed hard check is explained by one of the failed preconditions (`checks.explained_failures`, built on `checks.EXPLAINED_BY`). The rule: **a precondition explains only what "nothing happened" can cause: a missing expected change or missing evidence, never a failure that needs an actual wrong write.** A denied script call or a hook that never reached the model leaves changes out; it cannot change an item the prompt did not name, rename one, corrupt a tracker, write a file, commit or make a write attempt. So `not-permission-blocked`, `reminder-fired`, `reminder-delivered` and `plugin-under-test-isolated` explain `wanted-state` and `shown-by-script` (the wanted states and the table are missing), (`plugin-under-test-isolated` and `agent-completed` also explain `skill-loaded` and `skill-trigger`); they explain `timestamps-by-script`, `tracker-valid` and `tracker-created` only when the tracker is byte-identical before and after (or absent in both snapshots: then those fail only with "no tracker was created" or "updated was not refreshed"; a tracker that was written, wrongly or not, is graded on its own). `agent-completed` also explains every snapshot comparison (`others-untouched`, `quiet-when-nothing-changed` and the three above) when a snapshot is missing, because then nothing was compared.
- **FAIL** otherwise: any hard check fails with no failed precondition, **or** a failed hard check that no failed precondition explains. `others-untouched`, `written-by-script` and the gates that catch the agent's own misbehaviour (`no-direct-tracker-write`, `no-write-attempt`, `tracker-not-committed`, `nothing-else-changed`, `show-reads-only`, `no-tracker-when-negative`) are explained by no precondition: a script denial followed by a hand-written tracker is a FAIL, one call denied while another lands on the wrong item is a FAIL (not INCONCLUSIVE), a reminder run that finished before Stop (no marker) and also renamed an item is a FAIL, and a hand write before Stop with no marker is a FAIL. A pure "denied, nothing changed" run stays INCONCLUSIVE.

The exit code is 1 for FAIL or INCONCLUSIVE. How it plays out in the reminder cases: no hook report in the conversation and an unchanged tracker is INCONCLUSIVE (a blocking `hook_response` alone does not help); the report in the conversation and no outcome is FAIL; a **changed tracker** without the report passes `reminder-delivered` with the note "attributed by state only", and the outcome checks then grade the change, so a wrong or invented update is a FAIL. A run that did not complete (`agent-completed`: run note, error or missing result, missing snapshot) is INCONCLUSIVE in every case, offline regrades included: `state.json` also stores the run note, and a missing, unreadable or empty `state.json` is INCONCLUSIVE too (a fact visible in the trace, such as a direct Write of the tracker, still FAILs). An empty final reply is **not** a failed run.

Every check id has an invented run that fails it, and a test fails when one has none (`tests/test_checks.py`, `MUTATIONS`; `test_every_check_is_mutated`), the soft check included (its mutation fails it, and a test shows that the trial stays PASS). Each invented run fails exactly its own check. Regexes are tested against passing and failing commands and replies; the verdict tests cover a WARN-only trial as PASS with warnings.

## Run

```
make -C evals/milestones test                                              # offline, free, about 30 s
make -C evals/milestones eval ARGS="--only reminder-finishes --trials 1"   # REAL: one run, the canary
python3 evals/milestones/python/run_evals.py --fixtures DIR                # grade recorded runs offline (needs <id>.jsonl and <id>.state.json)
```

`--keep` keeps each trial's temporary directory (default: removed after the last snapshot); `--agent-cmd` replaces the whole command.

## A real run

- **Cost:** model calls on your own account; not measured yet. Each call is capped by `--max-budget-usd 2` (a ceiling per call, not an estimate). The suite is 10 single-turn cases, `reminder-finishes` first in the CSV. **Start with one case and `--trials 1`; the canary is `reminder-finishes`**: it is the only one that needs the Stop hook to run, to be delivered to the model and to be acted on, so it shows within one run which of the unconfirmed facts below hold. If it comes back INCONCLUSIVE, read the failures section of the report before spending on the rest.
- **Isolation:** each trial runs in `<tmp>/milestones-eval-<id>-*/ws`, a git repository whose **local** config sets identity, `commit.gpgsign=false`, `tag.gpgsign=false` and `core.hooksPath` to an empty directory beside the workspace; the child also gets `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` set to the null device. The command starts with `env -u` for `CLAUDE_PROJECT_DIR`, `CLAUDE_HOOK_RUNNING`, `MILESTONES_FILE`, `MILESTONES_NOW`, `MILESTONES_STALE_MINUTES` and the git variables `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE`, `GIT_COMMON_DIR`, `GIT_OBJECT_DIRECTORY`, `GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_PREFIX` (the runner merges `os.environ` and cannot unset), because an inherited `CLAUDE_PROJECT_DIR` would point the hook and the script at the repository you started the harness from, and an inherited `GIT_DIR` (harness started from a git hook) would point the agent's git at it. The harness's own git calls drop the same variables and, because the agent can write the workspace's `.git/config` and the snapshot runs git there afterwards, pass `-c core.fsmonitor=false -c core.hooksPath=/dev/null -c log.showSignature=false -c core.pager=cat -c diff.external=` (the known keys that name a program; not a complete defence, and the agent's own Bash has the same rights). It uses `--setting-sources project,local` and never `--bare` (which skips plugin hooks). The user's global gitignore does not apply in the fixture; the fixture ships its own `.gitignore`.
- **Permissions:** `--permission-mode dontAsk`. Edit and Write are granted on purpose, and so are `git add` and `git commit`, so that a direct tracker write or a commit of the tracker can happen and be measured. Plainly: the remote is not involved (there is none), but if headless Bash is not sandboxed, the agent's `git` runs with your rights in a temporary directory. Whether the sandbox applies is unconfirmed. The script is granted as `Bash(python3 *milestones.py *)`; if that pattern does not match the quoted absolute path the skill uses, the denial shows up as `not-permission-blocked` and the trial is INCONCLUSIVE (unless a gate that no precondition explains fails too).
- **Traces:** `artifacts/` (git-ignored) holds `<id>.jsonl`, `<id>.state.json` (before and after snapshots with the text of every small file) and `results.json`. They contain your paths and the model's session; review before sharing.
- **Needs `jq`** on the PATH for the reminder hook (the hook exits 0 silently without it, so `reminder-fired` would report INCONCLUSIVE).
- **Timeout:** 600 s per call, unmeasured.

## Limits

- `no-direct-tracker-write`, `no-write-attempt` and `written-by-script` read the trace, which shows only the main conversation. A subagent's write is caught by `timestamps-by-script` (state) only; a careful hand edit that fakes the timestamps is caught by nothing.
- `reminder-finishes` depends on the model judging that the slugify edit completes the milestone "Add slugify to textutil" (the names are made to match closely); expect variance and use `--trials`. The skill may also trigger without the hook if the agent reads `.cache`; `reminder-fired` proves the hook ran, not that it caused the update.
- The trigger cases deliberately avoid a `/milestones` prompt: the plan assumes a slash command expands without a Skill tool call (unconfirmed, not observed here), in which case the trigger check would fail on correct behaviour. Explicit invocation is not covered.
- `schema_check.py` is a second implementation of the schema beside `milestones.py validate()`. A test fails when the schema file uses a keyword it does not implement and compares both validators on a list of valid and invalid trackers; semantic disagreement outside that list is possible. It always reads the repository's schema, not the one under `--plugin`.
- `fed_to_model` matches the hook's text anywhere in a user, assistant or result event: an agent that reads `milestones-reminder.sh` would produce false evidence.
- `no-direct-tracker-write` is a pattern match on command segments, not a shell parser: a write hidden in a script file, a path held in a shell variable (`P=.cache/milestones.json; ... > $P`, `open(p, 'w')` where `p` is set in another segment), a decoded string, a tool not listed above or a command wrapped in `bash -c '...'` passes. A script write that the script itself or the permission system refused is still seen by `no-write-attempt`, but only as a `milestones.py` argv in the main conversation. A quote left open in a heredoc body can merge segments. The state backstop (`timestamps-by-script`, `written-by-script`) catches a hand write only when no script write call is beside it.
- `reply-names-current` is advisory (WARN): it reads wording, `claims_done` knows the phrasings above and nothing else, and a reply that evades it passes silently; a reply that trips it falsely only warns.
- A recorded trace from another machine regrades with the same verdicts only when its `plugins[]` entry has source `milestones@inline` (otherwise pass `--plugin` with the recorded path).

## Unconfirmed

Nothing below was observed in a real run of this harness. The shapes marked "recorded" were read from the recorded traces in `evals/oaat/artifacts/` (Claude Code 2.1.319, another plugin) and not copied.

- **Whether a blocking Stop hook continues the session inside one `claude -p` call.** `reminder-delivered` degrades to INCONCLUSIVE if not.
- **How its report reaches the stream-json trace.** The stub's encoding (a user text event) is invented. The field names of a `hook_response` system event (`hook_event`, `exit_code`), the shape of a `permission_denials` element and whether a system `permission_denied` event exists are undocumented here; the code matches on text and tolerates missing fields. `--include-hook-events` is a flag in `claude --help` (2.1.330); what it emits was not seen.
- **Whether hook processes inherit the `claude` process environment.** The harness does not depend on it: no `MILESTONES_STALE_MINUTES`, mtime backdating instead, and `env -u` for the variables above.
- **Whether `CLAUDE_PROJECT_DIR` in a `-p` run equals the working directory.** If not, the hook and the script look for the tracker elsewhere and `reminder-fired` is INCONCLUSIVE.
- **The spelling of the plugin skill.** The init event's `plugins[]` (`{"name", "source": "<name>@inline"}`) and `skills[]` (`oaat:oaat`) and the Skill call's `input.skill` were seen in recorded traces for `oaat`; `milestones:milestones` is by analogy. `skill_matches` compares after the last colon.
- **Whether the skill's `allowed-tools` pre-approves the script call in a headless `dontAsk` run, and whether `Bash(python3 *milestones.py *)` matches a quoted absolute path.** Reported as INCONCLUSIVE on a denial.
- **Whether `--setting-sources project,local` keeps your installed `milestones` plugin and user-level Stop hooks out.** If the user copy loaded too, the hook could run twice, and every trial is INCONCLUSIVE through `plugin-under-test-isolated`. Partial evidence for "it stays out": the recorded `oaat` traces, made with the same `--setting-sources`, show only `oaat@inline` although `oaat` is installed for that user.
- **Whether headless Bash is sandboxed**, and whether git there sees the fixture's local config as intended.
- **Whether a headless run creates `.claude/.cc-writes/` in the workspace** (only that path is ignored by the snapshot).
- **Whether a `/milestones` prompt produces a Skill tool call.** Assumed not; the cases avoid the slash form.
- **What `--max-budget-usd 2` does when it is hit** (exit code, result subtype) and what a run costs. `agent-completed` treats any non-zero exit, a result subtype other than `success` or `is_error` as INCONCLUSIVE, whichever the CLI does.
- **The shape of a failed Bash tool_result** (`is_error` set on a non-zero exit or a denied call, the text of a denial; `looks_denied` matches the words "permission ... denied" and "was denied", a guess) and **whether `permission_denials` elements carry `tool_use_id`.** `shown-by-script` and `not-permission-blocked` read both (a denial that shows only as an `is_error` tool_result, or as an element with a `tool_use_id` and no `tool_input`, is handled; whether Claude Code emits either is unconfirmed); a recorded tool_result has `content` as a string and no `is_error` when the call succeeded.
- **That `milestones.py show` prints the tracker's title in a Bash tool_result** (it does when run by hand, 2026-11-22; a long output could be truncated by the CLI).

## Provenance

`python/agent_trace.py` and `python/runner_cmd.py` are byte-identical copies of the files in [`evals/agent-md-audit/python/`](../agent-md-audit/python) (themselves copies of [`evals/oaat/python/`](../oaat/python)); `tests/test_plugin.py` fails if either drifts, and skips if the source is missing. If you fix one copy, fix all of them. `agent_trace.stats()` sums `total_cost_usd` over every result event, which double-counts a resumed session; the copies are not fixed (they stay byte-identical), `run_evals.py` takes the cost of the **last** result event instead. `python/run_evals.py`, `state.py`, `cases.py`, `fixtures.py` and `checks.py` are adapted from agent-md-audit; `hook_trace.py` and `schema_check.py` are new and local. Nothing in `evals/oaat` or `evals/agent-md-audit` was changed.
